# AgentSkill-Eval：一份通透理解

> 这不是知识点摘要，而是对项目本质、学习重点和工程取舍的提炼。  
> 完整手册：[AgentSkill-Eval 秋招知识与源码讲解手册](./AgentSkill-Eval_秋招知识与源码讲解手册.md)

---

## 1. 这个项目的本质不是 Agent，而是测量

表面上，项目包含：

- Agent Runtime；
- Skill；
- Tool；
- Trace；
- Benchmark；
- Optimizer；
- Dashboard。

但它真正解决的问题是：

> 如何知道一个 Skill 是否真的带来了增益？

Agent 只是在被测对象中运行。项目的核心价值来自测量设计：

```text
定义变量
-> 控制变量
-> 构造实验
-> 获取有效观测
-> 区分任务失败和测量失败
-> 估计效果
-> 限制结论
```

所以学习时，不要把最多时间花在“模型如何调用工具”，而要花在：

- 比较对象是否一致；
- Oracle 是否真的判断目标行为；
- 失败标签是否正确；
- 数据是否独立；
- 结论是否超过证据范围。

这是该项目与普通 Agent Demo 的根本区别。

---

## 2. 最难的问题不是执行，而是因果识别

假设 treatment 成功率比 control 高 20%，可能有多种原因：

```text
Skill 更好
模型随机波动
任务分配不同
第二次运行命中缓存
Provider 状态变化
预算不同
grader 异常
只挑选了有利结果
```

项目使用同题配对、固定配置、随机顺序和 repeats，尝试回答：

> 在其他因素尽量相同的条件下，只改变 Skill 会怎样？

这就是一种工程化的因果识别。

需要看清它的边界：

- 模型服务不能完全冻结；
- 相同 seed 不一定让云模型确定；
- 两次运行不可能共享完全相同的世界状态；
- 公开 Git Case 可能已进入预训练；
- 少量 cluster 无法支持强推断。

因此，可信评测不是“消除所有不确定性”，而是：

> 尽可能隔离不确定性，记录剩余不确定性，并限制结论。

---

## 3. PASS、FAIL、INVALID 是一条认识论边界

这三个标签不只是工程状态。

```text
PASS：
我有足够证据认为任务成功。

FAIL：
我有足够证据认为任务失败。

INVALID：
我没有足够证据判断任务能力。
```

INVALID 的价值在于承认“不知道”。

很多评测系统的问题不是算法差，而是拒绝承认未知：

- 网络失败被记成模型失败；
- 测试环境坏了被记成 Skill 回归；
- Trace 缺失却生成确定性归因；
- 数据不足却输出显著提升。

一个可信系统最重要的能力之一，是在证据不足时停止下结论。

---

## 4. Benchmark 比 Optimizer 更重要

如果 Benchmark 错误：

- Grader 永远通过，任何 Skill 都优秀；
- Grader 只接受参考补丁，正确替代方案被判错；
- 任务文本泄漏答案，Agent 只需复制；
- train 和 locked 重叠，优化结果虚高；
- baseline 已 100%，永远看不到提升。

无论搜索算法多复杂，都无法修复这些问题。

四态验证的深层意义：

```text
before-fail：
目标缺陷真实存在。

after-pass：
已知正确实现能够满足 Oracle。

mutation-fail：
Oracle 对关键行为敏感。

alternative-pass：
Oracle 判断行为，而不是匹配唯一实现。
```

对于新人，最值得亲手做的不是再加一个 Agent 框架，而是：

> 独立构造一个经得住四态验证的真实 Case。

这会同时训练 Git、测试、Oracle、数据泄漏和实验设计能力。

---

## 5. Evidence 有不同可信层级

“有哈希”不等于“完全可信”。

可以把证据分成五层：

| 层级 | 能证明什么 |
|---|---|
| 结构化记录 | 系统声称发生了什么 |
| 内容哈希 | 文件之后是否变化 |
| 原始 Trace/Artifact | 执行过程有哪些可观察事实 |
| 数字签名/Provenance | 谁生成、由什么流程生成 |
| 独立复现/第三方评测 | 外部主体能否得到一致结论 |

当前项目较强的是前 3 层，后 2 层仍有提升空间。

所以准确表达是：

> 内容寻址、可校验、篡改可检测。

而不是：

> 绝对不可篡改、第三方完全可信。

---

## 6. 软件架构实际上在模拟科学实验

项目的主要对象可以对应科学实验：

| 软件对象 | 科学实验含义 |
|---|---|
| ExperimentManifest | 预注册实验协议 |
| Variant | 对照组/处理组 |
| PairBlock | 配对样本 |
| Run | 一次实验分配 |
| Attempt | 一次物理实施 |
| Grader | 测量仪器 |
| Measurement | 观测值 |
| Manifest | 实验记录 |
| Statistics | 效果估计 |
| Confirmation | 独立复验 |
| Locked Test | 最终留出验证 |
| Promotion | 根据证据作发布决策 |

这解释了为什么项目需要：

- 冻结输入；
- 预注册阈值；
- 随机执行顺序；
- 原始证据；
- 失败分类；
- 独立 holdout；
- 负结果保留。

它不是为了“把系统做复杂”，而是把科学实验要求编码为软件约束。

## 7. 搜索结果天然乐观

假设生成 100 个完全无效的随机候选，每个都在小验证集上运行。

即使候选没有真实能力差异，也可能有一个因为随机波动看起来最好。

这就是多重比较和 selection bias。

```text
候选越多
-> 越容易出现偶然高分
-> search winner 越乐观
```

因此：

- validation_search 只用于选择；
- regression 检查已知能力；
- confirmation 检查独立泛化；
- locked test 限制最终反复试验。

“winner 不能直接发布”不是保守，而是搜索系统的必然要求。

---

## 8. 负结果是这个项目目前最真实的成果

真实 regression：

```text
base = 100%
winner = 100%
W/T/L = 0/4/0
```

这不是 Skill 提升证据，但提供了两条重要信息：

1. 门禁没有为了产出 v2 而降低标准；
2. Benchmark 在这一阶段没有提供提升空间。

正确的下一步不是继续修改 Skill，而是回到实验设计：

```text
先做 baseline screening
-> 找到中等难度 Case
-> 扩展多仓库独立样本
-> 再开始候选搜索
```

这体现一个重要工程能力：

> 能判断问题发生在被测对象、测量工具，还是实验设计。

## 9. 当前最深的数据问题是层级错位

项目把 defect family 当作 independence group，但一个 split 的多个 Case 来自同一仓库。

这些 Case 可能共享：

- 代码风格；
- 测试框架；
- 包结构；
- API 设计；
- 模型预训练熟悉度。

所以真正的数据层级更像：

```text
Repository
└── Defect Family
    └── Case
        └── Repeat
```

Repeat 不是独立 Case，Case 也未必独立于 Repository。

改进统计时，应先尊重数据生成过程，而不是先选择一个好看的统计公式。

## 10. 架构学习的重点不是模式名称

你可以背：

- Adapter；
- Repository；
- State Machine；
- DDD；
- CQRS；
- Content Addressing。

但面试官真正关心：

- 为什么这里需要它？
- 如果不用，会出现什么错误？
- 它保护了哪个 invariant？
- 它增加了什么复杂度？

例如 Runner Adapter：

```text
不用 Adapter：
实验核心理解每个 Runner 的参数和结果
-> 大量 if/else
-> 外部升级影响统计核心

使用 Adapter：
外部协议在边界完成翻译
-> 内部只依赖统一 Contract
```

只有能说明“问题、约束、选择、代价”，才算理解架构。

## 11. 新人最容易走偏的方向

### 误区一：先学所有 Agent 框架

LangChain、AutoGen、CrewAI 等框架不是理解 Agent 的前提。

先掌握：

- Agent loop；
- Tool schema；
- state；
- timeout；
- evaluator。

### 误区二：把模型输出当真值

真实环境状态和 grader 才是主要真值。

### 误区三：把测试数量当质量

304 个测试不自动证明实验结论正确。测试只能证明被覆盖的代码行为。

### 误区四：把系统复杂度当项目价值

84 个 CLI 命令不如一个真实、独立、可复验的 v1→v2 结果有说服力。

### 误区五：只展示最好看的数字

可信评测必须展示：

- invalid；
- Loss；
- 费用；
- 样本量；
- claim limit；
- 负结果。

## 12. 最有效的学习方向

学习投入按价值排序：

```text
第一优先：
Agent loop、Tool、Runtime、Oracle

第二优先：
配对实验、PASS/FAIL/INVALID、W/T/L

第三优先：
Benchmark 四态验证、数据泄漏

第四优先：
状态机、幂等、Adapter、原子存储

第五优先：
Bootstrap、McNemar、分层数据

第六优先：
Successive Halving、Pareto、Promotion

最后再学：
多 Agent、大规模调度、复杂 UI
```

## 13. 对秋招最有价值的能力证明

项目最终应该证明你具备：

1. 能把模糊问题定义为可测量对象；
2. 能设计可执行 Oracle；
3. 能区分业务失败和基础设施失败；
4. 能在外部系统边界使用 Adapter；
5. 能处理幂等、崩溃一致性和证据完整性；
6. 能理解数据泄漏和选择偏差；
7. 能保留负结果并限制结论；
8. 能指出自己系统的真实边界。

这些能力比“调用过几个大模型 API”更有区分度。

---

## 14. 一句话抓住整个项目

> AgentSkill-Eval 的本质，是把“我感觉这个 Skill 有用”变成一套可以控制变量、执行验证、保存证据、估计不确定性，并在证据不足时拒绝发布的工程协议。

学习这个项目的最终目标，也不是学会背它的模块，而是获得一种判断能力：

> 面对任何 Agent 改进，都先问改了什么、控制了什么、测量了什么、证据能支持多强的结论。
