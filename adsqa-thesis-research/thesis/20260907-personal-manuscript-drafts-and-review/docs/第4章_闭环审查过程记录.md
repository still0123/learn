## 与已有方法差异

### 1. 与普通 RAG 的差异

普通 RAG 通常是：

```text
用户问题 → 检索外部文档 → 拼接到 Prompt → 生成答案
```

第4章应强调本文不是单纯“问题驱动 RAG”，而是：

```text
用户问题 + 证据包中的 ASR/OCR/视觉标签/局部区域描述/证据置信度
→ 构造复合查询
→ 检索广告知识
→ 基于视频证据匹配程度重排序
→ 只注入能解释当前视频证据的知识
```

关键差异：

- 普通 RAG 的检索依据主要是问题文本；本文检索依据来自第3章证据包。
- 普通 RAG 容易把“稀缺效应、社会认同、情绪共鸣”等泛化概念注入任何广告策略题；本文要求知识条目必须与 ASR、OCR、视觉标签或局部证据匹配。
- 普通 RAG 只关心知识相关性；本文增加 `Ev(E, K_i)` 证据匹配项，要求知识能被视频线索触发。
- 普通 RAG 的知识可能替代视频事实；本文明确知识只能解释已有视频证据，不能生成不存在的品牌、价格、功效、受众或策略。
- 普通 RAG 的错误通常难以归因；本文把错误归因到知识误用、过度推断、OCR误读、ASR错配等类型。

建议第4章固定术语为：**证据驱动广告知识检索**，不要只写“广告知识 RAG”。

### 2. 与普通 CoT 的差异

普通 CoT 通常是：

```text
让模型一步步思考 → 输出推理过程和答案
```

第4章应强调本文不是自由链式思考，而是**结构化证据推理协议**：

```text
观察 → 知识匹配 → 分析 → 答案
```

关键差异：

- 普通 CoT 的中间步骤可能仍然是模型自由联想；本文把“观察”阶段限定为证据包中可见、可听、可读的信息。
- 普通 CoT 不区分事实证据与理论解释；本文显式设置“知识匹配”阶段，用于判断广告知识是否适用。
- 普通 CoT 容易把营销概念直接写进推理；本文要求先列证据，再匹配知识，再做营销分析。
- 普通 CoT 不一定能回溯证据来源；本文要求推理依赖证据包 ID、时间戳、局部框、ASR、OCR 和知识条目。
- 普通 CoT 主要提升推理流畅性；本文目标是提升证据一致性、知识一致性和可解释性。

因此第4章不宜称为“采用 CoT 提升推理能力”，应改为：**基于证据包的结构化广告语义推理协议**。

### 3. 与 Self-Refine / Reflection 的差异

Self-Refine / Reflection 通常是：

```text
初始答案 → 模型自评/反馈 → 根据反馈重写答案
```

第4章应强调本文不是让模型“再想一遍”，而是：

```text
初始答案 → 声明拆解 → 按声明类型确定所需证据 → 回查证据包和知识条目 → 输出判定与修正
```

关键差异：

- Self-Refine 多是整体答案级反馈；本文是声明级校验。
- Self-Refine 的反馈依据常是模型自身判断；本文要求每条声明绑定证据来源。
- 普通 Reflection 可能生成泛泛的“答案更完整/更准确”；本文输出 `claim_id`、`verdict`、`evidence_ids`、`error_type`、`revised_text`。
- Self-Refine 可能过度修改正确答案；本文通过 `CONFIRM / REVISE / REJECT / LOW_CONFIDENCE` 控制修改幅度。
- 普通反思不区分错误类型；本文区分视觉误读、OCR误读、ASR错配、时间错位、知识误用、过度推断、合规风险。
- 普通反思不要求营销声明同时满足“视频证据 + 知识条目”；本文明确营销推理声明必须双重支撑。

建议第4章统一称为：**声明级证据回溯式链式反思**，弱化“自我反思”说法。

### 4. 与 LLM-as-judge 的差异

LLM-as-judge 通常用于实验评估：

```text
标准答案 + 模型答案 → 裁判模型判断对错
```

第4章中的校验模块不应被写成普通 LLM-as-judge，而应定位为**生成前/生成中可靠性控制机制**。

关键差异：

- LLM-as-judge 是评价器，通常在实验阶段判断答案质量；本文反思校验是方法内部的一环，用于生成最终答案前的修正。
- LLM-as-judge 常做答案级二元评分；本文做声明级证据核查。
- LLM-as-judge 的依据可能是参考答案或评分标准；本文校验依据是证据包、ASR、OCR、局部 crop、知识条目。
- LLM-as-judge 关注“预测答案是否等价于标准答案”；本文关注“答案中的每条声明是否被证据支持”。
- LLM-as-judge 可能引入裁判偏差；本文仍需要在第5章额外验证校验器可靠性，例如人工一致率、Cohen’s Kappa、误修正率。

因此第4章应避免把校验模块写成“用大模型评价答案”，而应写成“基于证据包的声明级核查协议”。LLM-as-judge 只应出现在第5章实验评价中，并且需要人工一致性验证。

## 第4章风险提示

### 1. 最大风险：被认为是“普通 RAG + Prompt 反思”

当前第4章虽然已经引入证据包、证据匹配、声明拆解，但如果正文表述不够硬，仍可能被理解为：

```text
广告知识库 Top-K 检索
+ 观察—分析—答案 Prompt
+ 再让模型检查一次
```

这正是专利审查意见中被质疑的组合路径。需要避免把方法写成几个独立模块，而要把它们统一到“证据包生命周期”中。

### 2. RAG 部分技术强度偏弱

`/Users/bytedance/vqa_thesis_continue/rag_mvp/rag_retriever.py` 当前实现是轻量词袋检索、规则扩展和加权打分，优点是可解释、易复现，但也容易被质疑：

- 是否只是关键词匹配？
- `Ev(E, K_i)` 是否足够严谨？
- 权重 `0.55/0.20/0.20/0.05` 是否有调参依据？
- 阈值 `threshold=0.05` 是否过低？
- 查询扩展规则是否人工 Prompt 工程？
- 知识库 30 条是否规模太小？
- 知识来源 `marketing_common_knowledge` 是否缺少正式引用？
- 是否可能从 AdsQA 标签或答案中泄漏知识？

第4章需要明确：知识库不能从测试答案抽取；知识条目需给出来源、版本和风险说明；检索方法至少要有 no-RAG、random-RAG、generic-RAG、marketing-RAG、evidence-aware RAG 的消融。

### 3. “证据驱动”目前还需要更具体

第4章已经写了 ASR、OCR、视觉标签、局部证据描述，但还应更强绑定第3章证据包字段。例如：

- 检索查询中是否包含 `evidence_id` 对应的 OCR/ASR？
- 证据置信度是否影响检索？
- `source_type=prior` 的弱先验证据是否禁止作为事实依据？
- ASR 与视觉帧时间窗口是否进入检索？
- OCR 低置信度是否触发反思？
- 知识条目是否记录被哪些 evidence_id 触发？

如果没有这些机制，评委可能认为“证据包”只是换了一个输入名。

### 4. 结构化推理容易被认为是普通 CoT Prompt

“观察—知识匹配—分析—答案”相比普通 CoT 更稳，但仍可能被质疑为 Prompt 模板。需要补充：

- 每一阶段的输入约束；
- 每一阶段允许/禁止的声明类型；
- 观察阶段不得出现营销概念；
- 知识匹配阶段必须输出适用/不适用原因；
- 分析阶段必须引用观察证据和知识条目；
- 答案阶段必须保留不确定性表达；
- 输出最好带证据引用，如 `[E_003, K0005]`。

否则“结构化推理”技术含量不足。

### 5. 声明拆解与校验目前偏概念化

第4章已经有声明类型和校验规则，但还需要进一步落地：

- 声明如何自动拆解？
- 一个复杂句如何拆成多个声明？
- 如何识别视觉声明、文字声明、语音声明、营销推理声明？
- 每类声明如何绑定 required evidence？
- 如果一条声明需要多个证据包联合支持，如何计算支持度？
- 如何处理证据冲突？
- 如何避免反思模型把正确答案改错？

如果不补，容易被认为仍是“让模型检查自己”。

### 6. 触发策略容易被认为是工程规则

关键词触发在专利审查意见中已被认为是常规手段。第4章如果只写“价格、logo、why、say 触发反思”，风险较高。需要引入更可量化的风险分数：

```text
Risk = η1·OCR_uncertainty + η2·ASR_uncertainty + η3·RAG_conflict + η4·Response_entropy
```

并说明关键词触发只是基础策略，核心是证据风险触发和早停。

### 7. LLM-as-judge 实验风险

专利文本和已有材料中使用 DeepSeek-V3 作为裁判。若第5章继续使用 LLM judge，需要防止评委质疑：

- 自动裁判是否可靠？
- 是否偏向长答案？
- 是否偏向专业术语多的答案？
- 与人工判断一致性如何？
- 对营销策略题是否存在主观偏差？

第4章强化建议中应预留“人工一致性验证”和“裁判可靠性实验”。

### 8. “营销知识”有过度解释风险

广告问题天然容易产生过度阐释。风险包括：

- 视频只有普通促销文字，却强行解释为稀缺效应、损失规避；
- 视频有多人出现，就强行解释为社会认同；
- 家庭场景就强行解释为情绪共鸣；
- 出现专家/认证词就直接判断权威背书，但未核实真实性；
- 受众画像推断过度，如从人物年龄/职业做确定性判断。

第4章应强化限定表达：可能、倾向于、根据现有证据、证据不足无法确认。

## 第4章强化建议

### 1. 强化第4章总定位

建议第4章开头明确写成：

```text
第4章并不把 RAG、CoT 和反思作为彼此独立的增强模块，而是围绕第3章输出的证据包，完成从证据解释到证据校验的闭环。广告知识检索以证据包为查询来源，结构化推理以证据包为事实边界，链式反思以证据包为回溯对象。由此，第4章方法形成“证据包—知识检索—结构化推理—声明级回溯校验”的统一证据流。
```

### 2. 把“证据驱动广告知识检索”写得更技术化

建议补充以下机制：

- 检索查询从 `q` 扩展为：
  ```text
  Q_R = concat(q, ASR(E), OCR(E), visual_tags(E), local_evidence(E), global_summary(E), evidence_type(E))
  ```

- 检索得分保留现有形式，但强化证据匹配：
  ```text
  Score(K_i)=μ1 Sem(Q_R,K_i)+μ2 Key(Q_R,K_i)+μ3 Ev(E,K_i)+μ4 Prior(K_i)
  ```

- `Ev(E,K_i)` 不仅是词相似度，还应考虑：
  - ASR/OCR/视觉标签是否命中知识触发线索；
  - 命中线索是否来自高置信证据；
  - 是否来自真实检测而非 `prior`；
  - 是否与问题类型一致；
  - 是否存在反证或冲突证据。

- 建议每个被注入知识条目都记录：
  ```json
  {
    "knowledge_id": "K0005",
    "matched_evidence_ids": ["E_003", "E_007"],
    "matched_modalities": ["ocr", "asr"],
    "match_reason": "OCR出现限时抢购，ASR出现最后一天",
    "risk_notes": ["不得虚构库存或活动截止时间"]
  }
  ```

这样才能体现与普通 RAG 的实质差异。

### 3. 强化知识库来源和边界

当前知识库可用，但建议第4章增加：

- 知识条目不从测试集答案抽取，避免数据泄漏；
- 每条知识给出 `source`、`version` 和 `risk_notes`；
- 领域知识只解释已有证据，不产生视频事实；
- 合规类知识用于限制答案，不用于扩大推断；
- 明确知识库规模、类别、条目数和示例；
- 后续可扩展到教材、广告法合规规则、营销学公开资料。

建议将 `/Users/bytedance/vqa_thesis_continue/rag_mvp/marketing_knowledge_base_extended.json` 中 K0005 稀缺效应、K0004 社会认同、K0014 视觉隐喻、K0024 字幕承诺、K0029 证据一致性、K0030 知识一致性作为正文示例。

### 4. 强化结构化推理输出为“证据引用式”

建议把当前“观察—知识匹配—分析—答案”扩展为带证据引用的结构：

```text
1. 观察：
   - [E_003/OCR] 画面文字出现“限时抢购”
   - [E_004/ASR] 旁白提到“最后一天”

2. 知识匹配：
   - [K0005 稀缺效应] 适用，因 E_003 与 E_004 同时出现时间限制线索
   - [K0004 社会认同] 不适用，未发现销量、好评、用户推荐等证据

3. 分析：
   - E_003 + E_004 可解释为通过时间限制制造紧迫感，对应 K0005

4. 答案：
   - 该广告倾向于使用稀缺效应制造紧迫感，但不能进一步推断真实库存或活动截止时间。
```

这样可明显区别普通 CoT。

### 5. 把“链式反思”改成声明级证据核查算法

建议第4章强化为：

```text
初始答案 y0
→ 声明拆解 C={c1,...,cR}
→ 声明类型识别 type(c)
→ 所需证据映射 Req(type)
→ 证据回溯 Support(c,E,K)
→ 判定 verdict
→ 按判定更新答案
```

每个声明建议包含：

```json
{
  "claim_id": "C3",
  "claim_text": "广告使用稀缺效应制造紧迫感",
  "claim_type": "marketing_inference",
  "required_evidence": ["ocr_or_asr_scarcity_signal", "knowledge_entry"],
  "support_evidence_ids": ["E_003", "E_004"],
  "support_knowledge_ids": ["K0005"],
  "verdict": "CONFIRM",
  "error_type": "none"
}
```

这样可以把反思从 Prompt 技巧提升为可复现的校验流程。

### 6. 强化触发策略与早停机制

建议第4章将触发机制分两层：

第一层：问题类型触发  
- 文本细节：字幕、价格、数字、Logo；
- 语音内容：旁白、说了什么；
- 营销策略：策略、受众、情绪、隐喻；
- 因果解释：为什么、如何体现、作用；
- 高风险事实：功效、保证、第一、唯一。

第二层：证据风险触发  
- OCR 置信度低；
- ASR 置信度低；
- RAG 候选知识得分接近，概念冲突；
- 响应图分散，视觉定位不确定；
- 答案中出现无证据的营销概念；
- 答案中出现绝对化或功效性表达。

早停建议：

```text
若核心声明均有高置信证据支持，且 Risk ≤ ε，则直接输出；
否则进入声明级证据回溯校验。
```

这样比“关键词触发反思”更有技术含量。

## A3 技术审查 Agent 输出

技术问题

1. 第3章证据包承接总体成立，但接口不完全一致
- 草稿明确把第3章输出作为第4章入口，方向正确。
- 但第4章后续大量使用 `global_summary`、`visual_tags(E)`、`local_evidence(E)`、局部区域描述、响应图分布 `Response_entropy` 等信息，而 4.2.1 给出的证据包 schema 中没有这些字段。
- `global_view` 和 `local_high_resolution_evidence_view` 当前只包含 `view_id` 和 `resolution`，不足以支持“观察阶段描述画面内容”或“回查局部 crop”。需要说明第4章模型是否能直接访问图像视图，还是访问第3章生成的文本描述、视觉标签或 embedding。
- `source_type`、`modality_tags`、`ad_evidence_types` 三者边界不够清楚。当前既有来源、模态、广告语义类型，又有 `prior/weak_prior` 规则，但未给出枚举定义和字段级溯源规则。

2. RAG 检索打分框架合理，但实现细节不足以复现
- `Score(K_i)=0.55 Semantic + 0.20 Keyword + 0.20 Evidence + 0.05 Prior` 结构清晰，但 `Semantic`、`Keyword`、`Evidence`、`Prior` 的取值范围、归一化方法、阈值 `θ`、`θ_E`、`TopM` 均未定义。
- 草稿说 MVP 使用词袋和余弦相似度，但公式中仍称 `Semantic`，容易造成“语义检索”和“词袋检索”混用。若是词袋，应改为 lexical/bow similarity；若用 embedding，应说明模型、向量化字段和检索流程。
- `Conf(E)`、`SourceWeight(E)`、`TypeMatch(E,K_i)`、`QuestionMatch(q,K_i)` 都是关键项，但没有权重表、映射表或计算规则。
- `Conflict(E,K_i)` 的定义偏模糊。比如“只有普通价格，没有限时库存”不一定是冲突，更准确应是“证据不足”，不应作为负冲突。冲突应限于证据明确反驳知识适用条件的情况。
- 查询中直接拼接 `confidence`、`source_type` 等元数据，对词袋或向量检索未必有效。置信度和来源更适合作为结构化重排序特征，而不是纯文本 query token。

3. 证据匹配逻辑方向正确，但需要更强的门控约束
- 文中反复强调“知识只能解释证据，不能替代证据”，这是本章核心亮点。
- 但支持度公式和检索得分公式都是加权求和形式，存在高知识相似度或高先验分数弥补低证据匹配的风险。
- 对营销推理声明，应采用强门控：必须 `Ev(E,K_i) >= θ_E` 且至少存在强来源证据，不能只靠总分过线。
- `source_type=prior/weak_prior` 不能单独支撑事实这一原则正确，但需要字段级 provenance。否则一个证据包若同时含有 `prior` 和 `ocr`，系统无法判断哪个字段可支撑事实、哪个字段只是候选定位。

4. 结构化推理协议自洽，但输入输出边界仍需明确
- “观察—知识匹配—分析—答案”协议逻辑清楚，能有效区分视频事实与广告知识解释。
- 但需要明确初始答案 `y0` 到底是完整四段文本，还是只取最后“答案”部分进入声明拆解。
- 如果声明拆解对完整四段文本执行，观察和分析中的中间表达也会变成待校验声明，导致成本和噪声上升。
- 建议明确：结构化推理产生中间记录 `trace`，最终用户答案为 `answer_text`；声明拆解只针对 `answer_text` 和必要的核心分析句执行。

5. 声明拆解设计合理，但算法可执行性不足
- 声明类型划分为视觉、文字、语音、营销推理是合理的。
- 但声明拆解由谁执行未说明：规则、LLM、parser，还是混合方法。
- `candidate_evidence_ids` 和 `candidate_knowledge_ids` 如何生成也未定义。若依赖初始答案显式引用 evidence_id，则要规定生成阶段必须输出引用；若依赖语义匹配，则要说明匹配方法。
- `risk_level` 没有枚举标准和触发作用，当前只是字段占位。
- “核心声明”概念在早停中使用，但前文没有定义如何识别核心声明。

6. 校验规则总体合理，但判定阈值和支持度公式不够严谨
- `CONFIRM / REVISE / REJECT / LOW_CONFIDENCE` 四类判定清晰。
- 但 `Support(c_r,E,K)=S_E+S_K+S_M-S_C` 对营销推理不够安全。营销声明应满足视频证据和知识条目的双重必要条件，而不是加法补偿。
- 视觉、OCR、ASR、营销推理四类声明应分别定义最低支持条件。例如：
  - 文字声明：必须有非 prior 的 OCR 或局部图可读证据；
  - 语音声明：必须有 ASR 片段或人工转写证据；
  - 营销推理：必须同时有触发证据和知识条目；
  - 受众推断：必须有产品、场景、人物、语言风格等至少一种明确线索。
- `LOW_CONFIDENCE` 与 `REJECT` 的边界需要更明确：是证据缺失为 REJECT，证据存在但置信低为 LOW_CONFIDENCE；还是两者都可用于证据不足。

7. 触发策略存在顺序矛盾
- 4.8 中 `Claim_risk` 和 `CoreClaimsSupported(y0,E,K_E)` 都依赖声明识别。
- 但算法 4-1 中先执行步骤 6 触发判断，再执行步骤 7 声明拆解。
- 这会造成循环依赖：没有声明拆解，就无法计算声明风险和核心声明支持度。
- 需要调整为：
  - 先生成 `y0`；
  - 执行轻量声明抽取或核心声明识别；
  - 计算 `Claim_risk` 和 `CoreClaimsSupported`；
  - 再决定是否进入完整声明级校验。
- 或者明确 `Claim_risk` 是基于关键词和答案表层模式的粗估，不依赖完整声明拆解。

8. 早停策略和高风险触发之间关系不清
- 4.8.2 说高风险问题触发声明级校验。
- 4.8.4 又说若核心声明高置信且风险低可以早停。
- 需要明确二者优先级：
  - 高风险问题是否必然触发完整校验；
  - 还是高风险问题只提高 Risk 分数；
  - 若问题触发但证据高置信，是否允许早停。
- 建议表述为：关键词触发只是风险加权项，不是绝对规则；只有 `Risk > ε` 或核心声明不满足快速支持检查时才进入完整校验。

9. 第5章可验证性方向充分，但评价标签需求未交代
- 第5章消融设计比较完整，覆盖 no-RAG、random-RAG、generic-RAG、evidence-aware RAG、结构化推理、反思触发等。
- 但若要报告 Retrieval Recall@K、MRR、证据匹配率、声明级证据支持率、错误归因准确率，需要有知识条目标签、证据标签、声明支持标签或人工标注。
- AdsQA 原始数据未必自带这些标注。需要说明是否构建人工标注子集，标注哪些字段，规模多少，标注一致性如何。
- 自动裁判可靠性验证写得正确，但还需要说明内部校验模块本身也要被验证，不能只验证最终答案准确率。

10. 知识库构建需要更强的来源说明
- 当前 `source: marketing_common_knowledge` 过于笼统。
- 论文中应说明知识条目来自哪些公开教材、营销理论、广告合规规范或人工整理流程。
- 若知识库只有 30 条，应明确它是轻量原型，不应过度声称覆盖广告营销知识。
- 同时要防止知识库条目和测试集答案之间的数据泄漏，当前原则写到了，但需要在实验部分给出执行方式。

必须修改

1. 补齐第3章到第4章的正式接口
- 明确第3章实际输出字段。
- 若第4章需要 `visual_tags`、`global_summary`、`local_description`、`Response_entropy`，必须加入 schema 或说明由哪个模块生成。
- 明确图像视图 `view_id` 是否会作为多模态输入传给模型，还是只提供 OCR/ASR/视觉标签文本。

2. 定义字段枚举和字段级 provenance
- 给出 `source_type` 枚举：如 `visual_detection`、`ocr`、`logo_detection`、`asr`、`local_vlm`、`prior`、`weak_prior`。
- 区分 `source_type`、`modality_tags`、`ad_evidence_types`。
- 对 ASR、OCR、Logo、视觉标签、广告证据类型分别记录来源和置信度，避免一个证据包整体被误判为强证据或弱证据。

3. 重写 RAG 打分的可复现定义
- 定义 `Semantic/Keyword/Evidence/Prior` 的计算方式、归一化范围和阈值。
- 给出 `SourceWeight` 表、`TypeMatch` 映射表、`QuestionMatch` 问题类型映射。
- 明确 `θ`、`θ_E`、`TopM` 是固定超参、验证集调参，还是消融变量。

4. 修改证据匹配和声明支持的加法补偿问题
- 对营销推理声明使用门控式规则：
  - 必须有至少一个非 prior 的视频触发证据；

5. 修正触发策略的执行顺序
- 在算法中加入“轻量核心声明抽取/风险扫描”步骤，放在完整校验触发之前。
- 或将完整声明拆解提前到触发判断之前。
- 明确 `Claim_risk`、`CoreClaimsSupported` 的输入和计算方式。

6. 明确 `y0`、声明拆解对象和最终输出格式
- 说明 `y0` 是否包含观察、知识匹配、分析、答案四段。
- 建议声明拆解只针对最终答案和核心分析句，不对全部过程文本拆解。
- 给出最终答案 `y` 的格式要求：是否保留 evidence_id、knowledge_id，是否面向用户隐藏中间校验结果。

7. 补充第5章实验所需标注方案
- 若报告 Retrieval Recall@K 和 MRR，需要知识条目 ground truth。
- 若报告证据匹配率，需要 evidence-knowledge 匹配标注。
- 若报告声明级证据支持率，需要声明级人工标注或可信裁判验证。
- 若报告错误归因准确率，需要错误类型标签。

- 说明声画异步时如何判定“错配”与“合理邻域”。
- 否则语音声明校验规则无法落地。

可选优化

1. 将 `ocr_logo_text` 拆成 `ocr_text` 和 `logo_text`

## A4 创新性审查 Agent 输出

## A4 创新性审查结论

从评委/专利审查员视角看，当前第4章的核心风险是：**方法表述仍然过于像“广告场景下的 RAG + CoT Prompt + Self-Refine + LLM-as-judge 组合”**。草稿已经意识到这个风险，并在 4.2.3、4.10 中做了区分，但目前区分更多停留在“流程描述”和“原则声明”，还没有充分证明这是一个新的技术机制。

如果不进一步改写，审稿人很可能会认为：

1. **所谓广告知识增强，只是把普通 RAG 的知识库换成广告营销知识库。**
2. **所谓结构化广告语义推理，只是给 LLM 加了一个 Observation-Knowledge-Analysis-Answer 的 CoT Prompt。**
3. **所谓链式反思校验，只是 Self-Refine 的细粒度版本。**
4. **所谓声明级校验，本质上仍是 LLM-as-judge，只不过裁判对象从完整答案变成了 claim。**

因此，本章需要从“提示词流程”改写为“证据约束的推理控制机制”。创新性不能仅靠“广告知识库”“链式反思”“证据回溯”这些概念支撑，而必须落到以下三个技术对象上：

- **证据—知识绑定机制**：知识必须由具体 `evidence_id` 触发，而不是由问题触发。
- **声明—模态证据映射机制**：不同类型声明必须回查不同模态证据。
- **声明级动作更新机制**：最终答案不是自由重写，而是根据 `CONFIRM / REVISE / REJECT / LOW_CONFIDENCE` 对原子声明进行受控更新。

# 1. 关于“是否只是普通 RAG 换广告知识库”的质疑

## 1.1 审查意见

当前第4章确实存在被质疑为普通 RAG 的风险。

普通 RAG 是：

```text
问题 → 检索知识 → 拼接上下文 → 生成答案
```

本章当前流程是：

```text
问题 + 证据包 → 检索广告知识 → 拼接知识 → 生成答案
```

从表层看，区别只是检索输入多了证据包，知识库换成广告营销知识库。尤其是 4.3 和 4.4 中大量内容是知识库类别、关键词扩展、BM25/词袋/余弦相似度、Top-M 重排序，这些都属于 RAG 常规设计。

目前真正可能构成差异的部分是：

- `matched_evidence_ids`
- `source_type` 约束
- `Ev(E,K_i)` 证据匹配项
- `Conflict(E,K_i)` 冲突惩罚
- 无证据触发时不注入知识

但这些现在写得还不够硬，容易被认为只是普通 RAG 的重排序特征工程。

## 1.2 需要强化的创新点

建议把“证据驱动广告知识检索”改写成：

> **证据触发式知识许可机制**，而不是“增强检索”。

也就是说，知识条目不是简单被检索出来，而是必须通过一个“证据许可门控”才能进入推理上下文。

可以引入一个明确的三元关系：

\[
T(E_j, K_i, r)
\]

表示证据包 \(E_j\) 以触发关系 \(r\) 激活知识条目 \(K_i\)。例如：

```text
E_003: OCR="限时抢购"  →  K0005: 稀缺效应
触发关系: temporal_scarcity_signal
```

然后规定：

\[
K_i \in K_E
\iff
\exists E_j:
Trigger(E_j,K_i)=1
\land SourceValid(E_j)=1
\land Conf(E_j) \ge \tau_E
\land Conflict(E,K_i)=0
\]

这样就不是“检索到就用”，而是“证据许可后才能用”。

## 1.3 建议新增或改写内容

建议在 4.4 中增加一个小节：

### 建议新增：4.4.X 证据触发许可条件

可写为：

```text
与普通 RAG 不同，本文并不将检索得分最高的知识条目直接注入生成模型，而是要求知识条目必须满足证据触发许可条件。对于任一知识条目 K_i，只有当存在至少一个非 prior / weak_prior 来源的证据包 E_j，且 E_j 中的 ASR、OCR、视觉标签或广告证据类型与 K_i 的触发条件匹配时，K_i 才被允许进入推理阶段。
```

进一步定义：

```text
Allowed(K_i)=1 当且仅当：
1. 存在 matched_evidence_ids；
2. matched_evidence_ids 中至少一个证据来源不是 prior 或 weak_prior；
3. 证据置信度高于阈值；
4. 知识条目的 applicable_scenarios 与 ad_evidence_types 不冲突；
5. 不存在显式冲突证据。
```

这比当前的 `Score(K_i) >= θ` 更有新意，因为它把 RAG 从“相关性排序”变成了“证据许可”。

## 1.4 对当前文字的修改建议

当前表述：

> 本章采用证据驱动广告知识检索，而不是单纯问题驱动 RAG。

建议改为：

> 本章不将检索结果视为可直接使用的外部上下文，而是将其视为需要经过视频证据许可的候选解释。广告知识条目只有在被具体 `evidence_id` 触发、且触发证据满足来源、置信度和模态一致性约束时，才允许进入后续推理。因此，本章的知识增强不是“问题相关知识注入”，而是“证据许可的知识解释”。

# 2. 关于“是否只是 CoT Prompt”的质疑

## 2.1 审查意见

4.5 中的“观察—知识匹配—分析—答案”目前很容易被认为是一个 CoT Prompt 模板。虽然你强调“观察阶段不能使用营销概念”“知识匹配阶段判断知识是否适用”，但这些约束主要靠提示词执行，不是强机制。

评委可能会质疑：

> 你只是把 Chain-of-Thought 换成了固定格式，让模型分四步输出，并没有新的推理算法。

尤其是以下内容风险较高：

```text
请按以下结构输出：
1. 观察
2. 知识匹配
3. 分析
4. 答案
```

这看起来就是 Prompt Engineering。

## 2.2 需要强化的创新点

要避免被看成普通 CoT，需要把“观察—知识匹配—分析—答案”从自然语言模板改写成**受约束的中间状态转移**。

建议引入三类中间对象：

```text
Observation Tuple:
(evidence_id, modality, content, source_type, confidence)

Knowledge Match Tuple:
(knowledge_id, matched_evidence_ids, trigger_type, risk_note, allowed)

Analysis Link:
(claim_id, evidence_ids, knowledge_ids, inference_type, uncertainty)
```

也就是说，模型不是自由“想一想”，而是必须先生成结构化记录，再由这些记录组成答案。

## 2.3 建议新增机制

建议把 4.5 的标题从：

> 基于证据包的结构化广告语义推理

改成更有技术性的：

> 基于证据状态转移的广告语义解释生成

或者：

> 证据约束的观察—知识—声明生成协议

然后增加如下定义：

```text
本章不使用开放式 CoT，而是将中间推理过程约束为三个可检查状态：
S_o：观察状态，只包含来自证据包的事实元组；
S_k：知识许可状态，只包含被证据触发的知识条目；
S_c：声明生成状态，每个声明必须引用 S_o 与 S_k 中的元素。
```

形式化为：

\[
S_o = \{(evidence\_id, modality, text, source, confidence)\}
\]

\[
S_k = \{(knowledge\_id, matched\_evidence\_ids, trigger\_type, allowed)\}
\]

\[
S_c = \{(claim\_id, claim\_text, evidence\_ids, knowledge\_ids, uncertainty)\}
\]

最终答案由 \(S_c\) 线性化得到，而不是由模型自由生成。

## 2.4 对当前文字的修改建议

当前表述：

> 模型按照“观察—知识匹配—分析—答案”的协议生成初始答案。

建议改为：

> 系统首先将证据包转化为观察状态 \(S_o\)，再将检索知识转化为知识许可状态 \(S_k\)，随后仅允许模型基于 \(S_o\) 与 \(S_k\) 生成带有证据引用的声明集合 \(S_c\)。最终答案不是开放式 CoT 的自然语言结果，而是由可追溯声明集合线性化得到。

这样可以降低“只是 CoT Prompt”的嫌疑。

# 3. 关于“是否只是 Self-Refine”的质疑

## 3.1 审查意见

当前 4.6 和 4.7 的流程是：

```text
初始答案 → 声明拆解 → 判断声明是否正确 → 修改答案
```

这确实与 Self-Refine 高度相似：

```text
初始答案 → 自我反馈 → 重写答案
```

你的区别是“声明级”“证据级”“结构化 verdict”，但如果验证过程仍由同一个 LLM 根据提示词完成，审稿人仍可能认为这是 Self-Refine 的一种细粒度实现。

## 3.2 需要强化的创新点

必须强调：本章不是让模型“评价自己”，而是对每条声明执行**模态证据回查**。

建议将“反思”这个词降权。因为“链式反思”容易自动联想到 Reflection / Self-Refine。

可以改成：

- 声明级证据回溯校验
- 声明级证据一致性验证
- 证据约束的声明修正
- Claim-level Evidence-grounded Verification

建议少用：

- 反思
- 自我反思
- 再思考
- 自评

多用：

- 回查
- 校验
- 证据许可
- 声明更新
- 模态一致性检查

## 3.3 建议增加“更新约束”

当前最终答案更新仍然像自由重写。建议明确最终答案不是重新生成，而是按声明动作更新：

```text
CONFIRM: 原声明保留；
REVISE: 仅替换该声明，不修改其他声明；
REJECT: 删除该声明或替换为“证据不足”；
LOW_CONFIDENCE: 保留声明主体，但添加不确定性限定。
```

进一步写成：

\[
Update(c_r)=
\begin{cases}
c_r, & verdict=CONFIRM \\
revised\_text_r, & verdict=REVISE \\
\varnothing \text{ or uncertain statement}, & verdict=REJECT \\
hedge(c_r), & verdict=LOW\_CONFIDENCE
\end{cases}
\]

这样可以体现它不是 Self-Refine 的整体重写，而是受控编辑。

## 3.4 建议新增对比表述

当前表格已经有，但还不够尖锐。建议补充一行：

| 维度 | Self-Refine | 本文方法 |
|---|---|---|
| 修改自由度 | 可整体重写答案 | 只能对被标记声明执行保留、替换、删除或降置信 |
| 错误定位 | 依赖模型自然语言反馈 | 绑定 claim_id、evidence_id、knowledge_id 和 error_type |
| 证据机制 | 可无外部证据 | 每类声明必须满足模态证据要求 |
| 正确答案保护 | 容易 harmful correction | 通过 CONFIRM 保留机制限制无端改写 |

尤其要突出 **harmful correction rate**。这是区分 Self-Refine 的关键实验指标。

# 4. 关于“是否只是 LLM-as-judge”的质疑

## 4.1 审查意见

当前 4.7 的校验模块仍然可能被认为是 LLM-as-judge。因为它让模型输出：

```text
verdict: CONFIRM / REVISE / REJECT / LOW_CONFIDENCE
error_type
notes
```

这本质上就是让 LLM 当裁判。

你在 4.10.3 中说 LLM-as-judge 用于实验评价，而本文校验用于生成流程内部可靠性控制。这个区分是对的，但还不够。审稿人会继续追问：

> 只要是 LLM 判断答案是否被证据支持，不就是 LLM-as-judge 吗？

## 4.2 需要强化的创新点

需要将内部校验器描述为**证据约束的声明验证器**，而不是“裁判模型”。

区别不应只靠“使用阶段不同”，还要靠“判断依据不同”和“输出动作不同”。

建议强调：

1. LLM-as-judge 通常比较“模型答案”和“参考答案”。
2. 本文校验器不使用参考答案，而使用证据包和知识条目。
3. LLM-as-judge 输出评分或对错。
4. 本文校验器输出可执行编辑动作。
5. LLM-as-judge 面向样本级评价。
6. 本文校验器面向声明级证据绑定。

## 4.3 建议加入半规则化验证

为了进一步降低“LLM-as-judge”嫌疑，建议把部分校验写成规则或检索匹配，而不是全部交给 LLM。

例如：

### 文字声明

```text
OCR claim support = fuzzy_match(claim_text, ocr_logo_text) × OCR_confidence
```

### 语音声明

```text
ASR claim support = semantic_match(claim_text, asr_text) × ASR_confidence
```

### 营销推理声明

```text
marketing support = video_trigger_support × knowledge_trigger_support
```

### prior 限制

```text
if all supporting evidence source_type in {prior, weak_prior}:
    verdict cannot be CONFIRM
```

这种规则可以明确写入算法，而不是只写进 Prompt。

## 4.4 建议修改 4.10.3

当前表述：

> 本章方法不应被描述为“用大模型评价答案”，而应描述为“基于证据包的声明级核查协议”。

建议改为更强：

> 本章的声明级校验不以模型答案优劣为评价对象，也不输出样本级评分，而是对答案中的每个原子声明执行证据可满足性检查。其输入不是参考答案，而是第3章证据包、证据来源类型、模态置信度和被许可的知识条目；其输出也不是评价分数，而是对声明的保留、替换、删除或降置信动作。因此，该模块更接近生成过程中的证据一致性约束器，而非实验阶段的 LLM-as-judge。

# 5. 当前章节最容易被攻击的薄弱点

## 5.1 “广告知识库”过于轻量，创新性不足

当前写道：

> 当前轻量原型知识库包含 30 条广告营销知识条目。

这容易被质疑：

- 30 条知识是否足以构成知识库？
- 是否只是人工 Prompt 规则？
- 是否存在主观挑选？
- 是否从测试集答案中总结而来？
- 是否具有泛化性？

建议补强：

```text
轻量知识库仅用于验证机制有效性，本文创新点不在知识库规模，而在知识条目的证据触发、适用边界和风险约束结构。
```

同时增加：

- 知识来源列表；
- 构建流程；
- 去测试集泄漏说明；
- 知识条目版本管理；
- 扩展知识库实验；
- random / irrelevant / generic / marketing / evidence-aware RAG 消融。

## 5.2 `Ev(E,K_i)` 写得太抽象

当前公式：

\[
Ev(E,K_i)
=
\sum_{E_j \in E}
w(E_j,K_i)\cdot Match(E_j,K_i)
-
Conflict(E,K_i)
\]

这个形式太常规。建议进一步定义：

```text
Match(E_j,K_i)=1 当且仅当：
- OCR/ASR/visual tag 命中 K_i 的 trigger_terms，或
- ad_evidence_types 与 K_i 的 applicable_scenarios 匹配，或
- 局部证据描述与 K_i 的 trigger pattern 匹配。
```

并定义：

```text
SourceWeight(E_j)=
1.0, source_type 包含 OCR/ASR/local_high_resolution_evidence_view
0.7, source_type 包含 logo_detection/visual_detection
0.3, source_type 包含 weak_prior
0, source_type 仅为 prior 且无其他模态支持
```

这样更像可实现算法。

## 5.3 “提示词约束”缺少执行保障

当前多处使用：

- 不得虚构
- 必须引用
- 只能描述
- 应谨慎表达

这些是 Prompt 规则，不是技术机制。建议增加：

```text
如果某声明没有 evidence_id，则不允许进入最终答案；
如果某营销推理声明没有 knowledge_id，则不允许作为营销概念输出；
如果某 knowledge_id 没有 matched_evidence_ids，则不允许进入分析阶段。
```

## 六、各小节可执行修改建议

### 4.1 本章引言

建议调整重点：

1. 减少字段列表；
2. 强化“为什么需要第4章”；
3. 明确本章贡献。

建议将本章贡献概括为三点：

> 本章主要贡献包括：  
> 第一，提出证据驱动广告知识检索方法，使广告知识由证据包中的视频线索触发，而非仅由用户问题触发；  
> 第二，设计“观察—知识匹配—分析—答案”结构化推理协议，区分视频事实描述与广告知识解释；  
> 第三，提出声明级证据回溯式链式反思机制，对初始答案中的视觉、文字、语音和营销推理声明逐条核查并修正。

### 4.2 证据包接口与方法总体框架

建议补充“本章输入输出边界”：

- 输入：用户问题 \(q\)、证据包集合 \(E\)、广告知识库 \(K\)；
- 中间输出：检索知识集合 \(K_E\)、初始答案 \(y_0\)、声明集合 \(C\)、校验结果 \(V\)；
- 输出：最终答案 \(y\)。

建议在4.2.2中加入中间变量：

\[
K_E=\{K_i \mid Score(K_i)\ge \theta, Ev(E,K_i)\ge \theta_E\}
\]

\[
V=\{v_1,v_2,\ldots,v_R\}
\]

这样后续4.4、4.7、4.11会更连贯。

### 4.3 广告营销知识库构建

建议加强“知识库不是答案库”的表述。

可增加一句：

> 该知识库不存储具体视频答案，而存储广告概念、适用条件和风险边界，用于解释证据包中已经出现的营销线索。

建议将“当前轻量原型知识库包含30条”改为更谨慎：

> 本文原型阶段构建了包含30条条目的轻量广告营销知识库，用于验证方法流程和消融设置。后续实验中需进一步说明知识来源、版本控制和扩展策略。

### 4.4 证据驱动广告知识检索

本节是核心，应突出“证据驱动”与“证据感知重排序”的区别。

建议增加定义：

> 证据驱动广告知识检索强调召回阶段的查询构造，即检索查询由用户问题和证据包共同构成；证据感知重排序强调排序阶段的知识过滤，即仅保留能够被当前视频证据触发的知识条目。

这样可以避免两个术语混淆。

### 4.5 基于证据包的结构化广告语义推理

建议标题改为：

> 4.5 基于“观察—知识匹配—分析—答案”的结构化广告语义推理

这样核心术语更突出。

4.5.1中的表格很好，但建议将“禁止内容”写得更论文化：

- “无证据补全” → “缺乏证据支撑的事实补全”
- “强行套用” → “套用未被证据触发的营销概念”
- “删除不确定性” → “省略必要的不确定性限定”

### 4.6 初始答案声明拆解

建议明确“声明拆解”与“校验”的边界：

> 声明拆解阶段只负责将答案转化为可核查单元，并不判断声明真伪；声明真伪由4.7的证据回溯校验阶段完成。

这样可避免读者误以为拆解阶段已经完成判断。

### 4.7 声明级证据回溯式链式反思校验

建议标题保持完整术语：

> 4.7 声明级证据回溯式链式反思

小节中可简称“声明级回溯反思”。

建议将“链式反思”定义得更明确：

> 本文所谓“链式”并非指自由展开的隐式推理链，而是指“声明拆解—证据映射—逐条核查—判定修正—答案更新”的显式核查链。

这能避免被误解为普通CoT或Self-Reflection。
