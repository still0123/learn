# P6 创新点候选：另案重申请方向

## 执行判断

本轮不再围绕原案“基于视听协同感知与链式校验的广告视频问答方法”做复审式补强，而是把第一轮报告中不宜直接塞回原案的工程化证据层拆出来，设计为另案重申请主题。

建议新案总主线命名为：

> 一种基于问题驱动证据路由与一致性图谱的可信广告视频问答方法、装置、设备及介质。

新案核心不应写成“RAG + CoT + Reflection + OCR/ASR”的组合，而应写成：

> 对多模态证据进行统一封装，依据问题类型进行证据路由，在问题语义、视觉局部证据、ASR、OCR/Logo 与广告知识之间构建一致性图谱，并在生成答案前后利用冲突仲裁与可信证据包约束生成，保证答案中的每个关键声明均可回溯到相容证据集合。

第一轮结论已指出 `evidence package / evidence ID` 原始公开支持弱，适合继续申请/新申请；现有代码已有 `EvidencePackage`、`EvidenceField`、`evidence_id`、ASR/OCR/logo/global/local 字段以及 `claim_checker.py` 的声明类型到证据类型路由雏形，但尚未实现完整一致性图谱、冲突仲裁和约束生成。因此本文件将其定位为“另案重申请候选”，不是声称原案已完整公开或代码已完整实现。

## I-01：问题驱动的多模态证据路由方法

### 1. 技术机制

- 核心步骤：
  1. 接收广告视频问答请求后，将用户问题和初始/候选答案拆分为多个声明单元；
  2. 对每个声明单元识别声明类型，包括 OCR/Logo 文字声明、ASR 语音声明、营销策略声明、视觉对象/动作声明、因果推理声明；
  3. 为不同声明类型生成所需证据清单，例如文字声明绑定 `ocr + logo_detection + local_view`，语音声明绑定 `asr + time_window`，营销声明绑定 `video_evidence + marketing_knowledge`；
  4. 按证据清单从统一证据包中选择证据字段，并生成每个声明的证据路由记录；
  5. 将证据路由记录交给后续一致性检查、冲突仲裁或约束生成模块。
- 输入：用户问题、广告视频证据包、候选答案或待验证声明、问题/声明类型识别规则。
- 输出：`claim_id -> required_evidence_types -> evidence_ids -> route_status` 的结构化证据路由表。
- 与现有流程的连接点：位于“证据定位”和“证据校验”之间，是把原案 S2/S3/S5 串成可信闭环的入口。

### 2. 为什么不是模块拼接

- 不是简单地把 OCR、ASR、RAG 都喂给模型，而是根据“问题/声明类型”动态决定必须引用哪些证据源。
- 关键耦合关系：声明类型决定证据类型，证据类型决定可用 evidence package 字段，字段缺失会触发降级、补检索或拒答。
- 解决的广告视频特有技术问题：广告问答经常同时涉及“画面中是否出现文字”“旁白说了什么”“为什么这是稀缺性策略”等不同证据粒度；统一输入容易导致模型用不相关证据回答高风险问题。

### 3. 原始公开与本地支持

| 支持点 | 本地来源路径 | 摘录/章节 | 支撑强度 |
|---|---|---|---|
| 原案高风险触发与多模态证据回溯 | `source_texts/patent_docx.txt` | S51-S52：触发条件、回溯视频与音频证据 | 中 |
| 原案多模态证据来源 | `source_texts/patent_docx.txt` | S2/S3/S4：双流视觉、ASR、OCR、专家上下文 | 中 |
| 声明类型到证据类型的代码雏形 | `code_refactor/reflection/claim_checker.py` | `infer_claim_type()` 为 OCR/logo、ASR、marketing、visual 声明返回不同 `required_evidence` | 强 |
| 统一证据包字段 | `code_refactor/evidence/evidence_package.py` | `EvidencePackage` 包含 `asr`、`ocr_text`、`logo_text`、`global_view`、`local_high_resolution_evidence_view`、`ad_evidence_types` | 强 |
| 第一轮用途判断 | `runs/patent-analysis-20260623-round01/10_final_recommendation.md` | 将 evidence package / evidence ID 归入继续申请/新申请 | 强 |

### 4. 与原被驳回方案的差异

- 原案主线：先生成双流视觉表征和知识上下文，再用结构化链式推理生成答案，触发式校验作为后处理。
- 新案主线：先把问题/声明转化为证据需求，再根据需求路由证据；生成和校验都必须服从路由结果。
- 差异重点：从“答案类型/触发词决定是否反思”升级为“声明类型决定证据路径和证据最低配置”。

### 5. 技术效果

- 可合理主张的技术效果：减少证据使用错配；使文字、语音、视觉、营销知识类声明分别回溯到对应证据类型；提升广告视频问答输出的可核查性。
- 不能主张或需实验补充的效果：准确率提升比例、幻觉率下降比例、推理速度提升。

### 6. 权利要求路径

- 适合写入新案独立权利要求：是。
- 适合写入从属权利要求：是。
- 推荐限定语：对候选答案中的声明进行类型识别，基于声明类型生成所需证据类型集合，并从统一证据包中选择满足所需证据类型的证据项；当证据项不满足最低配置时，触发补充检索、降级生成或拒答。
- 新增内容风险：中。原案有触发校验和多模态证据，但“声明级路由表”需要作为新案新增设计，不宜声称原案已明确公开。

### 7. 代码落点和难度

- 现有代码支撑：`claim_checker.py` 的 `ClaimCheckPlan.required_evidence`；`evidence_package.py` 的统一字段。
- 需要新增实现：`evidence/router.py`，包含 `ClaimEvidenceRoute`、`EvidenceRequirement`、`route_claims_to_evidence()`、缺失证据处理策略。
- 难度：中。文本级 MVP 可快速实现；视觉/OCR/Logo 真实证据接入需要额外工程。
- 主要风险：如果只停留在关键词规则，容易被认为是业务规则或提示词工程；需要把“证据最低配置”和“缺失证据控制生成”写成技术约束。

### 8. 模拟审查员攻击预测

- 可能攻击点：按问题类型选择证据是常规规则路由；把 OCR/ASR/RAG 分流属于显而易见工程设计。
- 反制证据：新案不只路由输入，而是把声明、证据类型、证据 ID、生成许可状态绑定，并将证据缺失转化为生成约束或拒答策略。
- 仍需补强：补一个最小实验或日志样例，展示同一广告问题下文字声明、语音声明、营销声明走不同证据路线。

### 9. 建议

保留，作为新案独立权利要求的入口特征。

## I-02：多模态证据一致性图谱构建方法

### 1. 技术机制

- 核心步骤：
  1. 将广告视频中的关键帧、局部裁剪区域、OCR 文本、Logo 文本、ASR 片段、广告知识条目和问题/声明分别表示为图节点；
  2. 在节点之间建立同源、时间邻近、空间包含、语义支持、语义冲突、知识解释等边；
  3. 对每条边计算一致性得分或冲突得分，例如 ASR 时间窗口与当前帧是否邻近，OCR 文本是否支持答案中的价格/品牌声明，营销知识是否被视频证据触发；
  4. 针对每个待回答声明提取其支持子图，并将支持子图作为可信证据包的一部分；
  5. 将图谱中的低一致性边、孤立节点或冲突节点交给冲突仲裁模块。
- 输入：统一证据包、问题和声明路由表、时间戳、局部/全局视觉证据、ASR/OCR/Logo 文本、广告知识条目。
- 输出：多模态证据一致性图谱、声明支持子图、一致性评分和冲突列表。
- 与现有流程的连接点：把原案“响应图/双流表征/知识检索/回溯校验”转化为统一可计算的证据关系层。

### 2. 为什么不是模块拼接

- 不是把多模态证据简单拼成上下文，而是显式建模证据之间的支持、冲突和解释关系。
- 关键耦合关系：ASR 时间窗口、局部 OCR、Logo、视觉标签和知识条目必须在同一声明支持子图内达到一致性阈值，才能被用于生成高置信答案。
- 解决的广告视频特有技术问题：广告中旁白、画面和文字可能故意不同步或使用隐喻；单个模态看似支持的结论，可能与另一个模态冲突。

### 3. 原始公开与本地支持

| 支持点 | 本地来源路径 | 摘录/章节 | 支撑强度 |
|---|---|---|---|
| 原案响应图和声画异步处理 | `source_texts/patent_docx.txt` | S21-S22：问题、ASR、OCR 共同生成综合响应图，并用滑动窗口处理声画异步 | 中 |
| 原案全局/局部双流和知识检索 | `source_texts/patent_docx.txt` | S23、S3、S4：局部精细视角、专家上下文、联合推理 | 中 |
| 原案多模态证据回溯 | `source_texts/patent_docx.txt` | S52：回溯视频与音频证据 | 中 |
| 统一证据字段 | `code_refactor/evidence/evidence_package.py` | `time_window`、`global_view`、`local_high_resolution_evidence_view`、`asr`、`ocr_text`、`logo_text`、`ad_evidence_types` | 强 |
| 第一轮风险定位 | `runs/patent-analysis-20260623-round01/10_final_recommendation.md` | 认为软件架构化证据层适合继续申请/新申请 | 强 |

### 4. 与原被驳回方案的差异

- 原案的“响应图”主要用于定位和裁剪，审查员容易拆解为热力图、跨模态对齐、局部 ROI。
- 新案的“一致性图谱”不是视觉热力图，而是跨证据节点的关系图，用于判断多模态证据是否相互支持或冲突。
- 差异重点：从“哪里看”转为“哪些证据共同支持同一声明、哪些证据彼此冲突”。

### 5. 技术效果

- 可合理主张的技术效果：提高答案依据的可追溯性；在声画异步和营销隐喻场景下识别跨模态证据不一致；避免单一模态证据误导生成。
- 不能主张或需实验补充的效果：图谱一定优于所有 RAG/CoT 方法、准确率显著提升。

### 6. 权利要求路径

- 适合写入新案独立权利要求：是，建议作为核心特征。
- 适合写入从属权利要求：是。
- 推荐限定语：将多模态证据项构造为图节点，并基于时间邻近、空间包含、语义支持、语义冲突和知识解释关系生成边；针对待回答声明提取支持子图，并基于支持子图的一致性得分控制答案生成。
- 新增内容风险：中高。原案没有明确“图谱节点/边/一致性评分”的完整公开，适合新申请，不适合直接加回原案。

### 7. 代码落点和难度

- 现有代码支撑：`EvidencePackage` 已具备节点字段基础；`ad_evidence_types` 可作为广告知识或营销类别节点。
- 需要新增实现：`evidence/consistency_graph.py`，包含 `EvidenceNode`、`EvidenceEdge`、`ConsistencyGraph`、`build_graph_from_package()`、`extract_support_subgraph()`。
- 难度：中到高。文本/元数据图谱 MVP 中等；真实视觉空间包含、OCR bbox、Logo bbox 需要更高成本。
- 主要风险：如果图谱只用字符串相似度，会被认为是普通知识图谱或检索排序；需要限定多模态时间/空间/语义关系共同参与。

### 8. 模拟审查员攻击预测

- 可能攻击点：知识图谱、证据图、检索增强生成已有公开；把多模态证据做图是常规可视化或工程表示。
- 反制证据：本方案的图边不是泛化知识关系，而是广告视频问答中的时间邻近、局部视觉包含、OCR/Logo 支持、ASR 支持、营销知识解释和冲突边，用于约束生成。
- 仍需补强：需要外部检索确认是否已有“multimodal evidence graph for VQA/fact verification”类似公开。

### 9. 建议

保留，作为新案最有区分度的核心创新点。

## I-03：跨模态冲突检测与仲裁机制

### 1. 技术机制

- 核心步骤：
  1. 在一致性图谱中识别冲突模式，包括 OCR 与答案文本不一致、ASR 与视觉场景不一致、营销知识条目缺少视频证据触发、局部视图与全局视图语义不一致；
  2. 为不同冲突类型设置仲裁优先级，例如价格/数字类声明优先信任 OCR/local view，旁白类声明优先信任 ASR/time window，策略类声明必须同时满足视频证据和营销知识；
  3. 当证据冲突无法满足最低仲裁规则时，生成“不足以支持”的生成约束，而不是强行输出确定答案；
  4. 当冲突可仲裁时，输出被采信证据、被抑制证据和仲裁理由；
  5. 将仲裁结果写入可信证据包，供答案生成和后验校验复用。
- 输入：一致性图谱、声明路由表、证据字段置信度、证据类型优先级、问题类型。
- 输出：冲突列表、仲裁结果、采信证据集合、生成约束。
- 与现有流程的连接点：位于证据图谱与可信证据包之间，负责把多证据不一致转化为可执行的生成约束。

### 2. 为什么不是模块拼接

- 不是通用 self-reflection，因为仲裁发生在生成之前或生成过程中，依据结构化证据关系而不是让模型“再想一遍”。
- 关键耦合关系：问题类型决定仲裁规则，仲裁规则决定哪类证据可作为最终声明依据。
- 解决的广告视频特有技术问题：广告常存在旁白夸张、画面隐喻、字幕促销条款短暂出现、Logo 与口播不同步等跨模态冲突。

### 3. 原始公开与本地支持

| 支持点 | 本地来源路径 | 摘录/章节 | 支撑强度 |
|---|---|---|---|
| 原案声画异步问题 | `source_texts/patent_docx.txt` | 背景技术和 S22：广告视频声画非同步、时序滑动窗口聚合 | 中 |
| 原案事实核查与修正 | `source_texts/patent_docx.txt` | S51-S53：触发事实核查、确认令牌/修正令牌 | 中 |
| 证据类型路由雏形 | `code_refactor/reflection/claim_checker.py` | 不同声明类型返回不同 `required_evidence` | 强 |
| 证据字段和置信度字段 | `code_refactor/evidence/evidence_package.py` | `EvidenceField.confidence`、`scores`、`prior_flag` | 强 |

### 4. 与原被驳回方案的差异

- 原案的链式校验是生成后核查，容易被 D2/FEVER 类文本验证吸收。
- 新案的冲突仲裁是多模态证据层的规则化决策，不依赖模型自由反思；它输出采信/抑制证据和生成约束。
- 差异重点：从“反馈令牌修正答案”升级为“冲突证据无法通过仲裁时限制答案声明强度”。

### 5. 技术效果

- 可合理主张的技术效果：降低跨模态证据冲突导致的错误确定性回答；在高风险问题中保留冲突来源和仲裁依据。
- 不能主张或需实验补充的效果：完全消除幻觉、必然提升所有问题准确率。

### 6. 权利要求路径

- 适合写入新案独立权利要求：建议作为与 I-02 配套的核心特征。
- 适合写入从属权利要求：是。
- 推荐限定语：当同一声明对应的至少两个证据节点之间存在语义冲突或时空不一致时，根据声明类型选择预设仲裁优先级；若冲突证据未满足仲裁阈值，则生成降级答案或证据不足提示。
- 新增内容风险：中。原案有校验和声画异步，但没有清楚公开仲裁优先级和证据抑制。

### 7. 代码落点和难度

- 现有代码支撑：`EvidenceField.confidence`、`scores` 可承载置信度；`claim_checker.py` 可承载声明类型。
- 需要新增实现：`evidence/conflict_arbiter.py`，包含 `ConflictType`、`ArbitrationRule`、`ArbitrationResult`、`detect_conflicts()`、`arbitrate_conflicts()`。
- 难度：中。规则仲裁可先做 MVP；语义冲突检测需要 embedding/NLI 或模型辅助。
- 主要风险：规则过硬会显得像人工业务规则，规则过软又会退化成提示词；应强调其对证据类型、时空关系和生成许可的技术控制。

### 8. 模拟审查员攻击预测

- 可能攻击点：冲突检测、置信度排序、证据优先级是常规数据融合技术。
- 反制证据：新案的仲裁规则绑定广告视频问答的具体声明类型和证据形态，例如价格文字优先 OCR/local view，旁白内容优先 ASR/time window，营销策略必须具备视频证据和知识解释双支持。
- 仍需补强：需补充典型冲突例子和仲裁前后输出差异。

### 9. 建议

保留，作为 I-02 的强配套特征。

## I-04：可信证据包约束生成机制

### 1. 技术机制

- 核心步骤：
  1. 将路由结果、一致性子图、冲突仲裁结果封装为可信证据包；
  2. 为可信证据包中的每个证据项分配 evidence ID、证据类型、来源字段、时间窗口、局部/全局视图引用、置信度和可用状态；
  3. 在提示词或解码约束中要求模型的每个关键答案声明引用至少一个满足路由要求且通过仲裁的 evidence ID；
  4. 对没有足够 evidence ID 支撑的声明进行自动降级、改写或阻断；
  5. 生成答案后输出声明到 evidence ID 的引用表，供后续校验和人工复核。
- 输入：路由表、一致性图谱子图、仲裁结果、候选答案或生成模板。
- 输出：可信证据包、证据约束提示、最终答案、声明-证据引用表。
- 与现有流程的连接点：替代原案中较泛的“观察-分析-推理-答案”协议，使结构化生成被具体证据项约束。

### 2. 为什么不是模块拼接

- 不是普通 prompt engineering，因为它要求生成内容受 evidence ID、证据类型和仲裁状态约束。
- 关键耦合关系：生成许可由证据包给出，模型不能自由引用未通过路由/一致性/仲裁的证据。
- 解决的广告视频特有技术问题：广告解释往往包含营销意图、受众画像和视觉隐喻等抽象结论；没有证据包约束时，模型容易用常识补全而不是视频证据支撑。

## I-05：面向广告问答的证据缺失降级与可审计日志机制

### 1. 技术机制

- 核心步骤：
  1. 在证据路由、一致性图谱或冲突仲裁任一阶段记录证据缺失、证据冲突或证据置信度不足事件；
  2. 根据缺失证据类型选择降级策略，例如缺少 OCR 时禁止确定价格/文字声明，缺少 ASR 时间窗口时禁止确定旁白内容，缺少视频证据时禁止强营销策略结论；
  3. 输出降级后的答案表达，例如“画面证据不足以确认”“仅能根据旁白推断”“需要更多帧/OCR 结果支持”；
  4. 生成可审计日志，记录 claim ID、所需证据、实际证据、冲突证据、仲裁规则和最终输出策略；
  5. 将日志用于后续模型评估、人工复核或二次证据补采。
- 输入：路由失败记录、一致性评分、冲突仲裁结果、生成前候选声明。
- 输出：降级生成策略、可审计日志、证据补采任务。
- 与现有流程的连接点：为可信证据包约束生成提供安全出口，避免证据不足时模型仍生成强结论。

### 2. 为什么不是模块拼接

- 不是简单输出“不知道”，而是按缺失证据类型和声明类型执行有差别的降级。
- 关键耦合关系：证据路由失败原因决定答案降级方式，审计日志反向记录所有证据控制决策。
- 解决的广告视频特有技术问题：广告答案常涉及商业意图和说服策略，证据不足时需要可解释地降低结论强度，而不是产生确定性营销解读。

### 3. 原始公开与本地支持

| 支持点 | 本地来源路径 | 摘录/章节 | 支撑强度 |
|---|---|---|---|
| 原案事实核查和修正 | `source_texts/patent_docx.txt` | S51-S53：检测、核查、确认/修正 | 弱到中 |
| 原案可信度/鲁棒性目标 | `source_texts/patent_docx.txt` | 背景和技术效果：减少幻觉、提升可信度 | 弱 |
| 证据包可序列化 | `code_refactor/evidence/evidence_package.py` | `to_dict()`、`traceable_to_raw`、`prior_flag`、`scores` | 强 |
| 第一轮风险提示 | `runs/patent-analysis-20260623-round01/10_final_recommendation.md` | 不得主张未经实验支撑的性能收益，证据层适合新申请 | 强 |

### 4. 与原被驳回方案的差异

- 原案是“校验后确认或修正答案”，仍可能被理解为普通反思。
- 新案是“证据不足时控制答案声明强度，并留下可审计日志”，属于可信生成控制和系统审计。

### 5. 技术效果

- 不能主张或需实验补充的效果：完全避免错误、直接提升模型性能。

## 推荐组合

### 最推荐的新案组合

1. I-01 问题驱动证据路由：确定每个声明需要什么证据；
2. I-02 多模态证据一致性图谱：判断证据之间是否互相支持；
3. I-03 跨模态冲突仲裁：处理广告视频常见的声画/文字/知识冲突；
4. I-04 可信证据包约束生成：只允许通过证据控制的声明进入答案；
5. I-05 证据缺失降级与审计日志：作为安全出口和从属实施例。

### 适合的新案独立权利要求骨架

- 获取广告视频的多模态证据并构造包含 evidence ID 的统一证据包；
- 对用户问题或候选答案声明进行类型识别，并基于类型生成证据路由；
- 基于路由得到的证据项构建多模态证据一致性图谱；
- 根据一致性图谱检测跨模态冲突并执行仲裁；
- 将通过仲裁的证据项封装为可信证据包，并以可信证据包约束答案生成，使答案声明引用对应 evidence ID；
- 对证据不足或冲突无法仲裁的声明执行降级、阻断或补证。

### 本轮风险结论

- 最大优势：新案主线从“模型推理方法”转为“证据控制层方法”，更能避开原驳回中对 RAG、CoT、自验证、热力图的拆解攻击。
- 最大风险：一致性图谱、冲突仲裁、证据包约束生成需要补实现和例子；否则容易被审查员认为是抽象规则或普通工程日志。
- 代理人加工重点：不要把权利要求写成“使用大模型进行推理并引用证据”，而要写成“证据路由、一致性图谱、冲突仲裁、可信证据包约束生成”的数据结构和控制流程。

### 需要补的材料

- 一个最小运行例：同一广告问题中，价格声明走 OCR/local view，旁白声明走 ASR/time window，营销策略声明走 video evidence + marketing knowledge。
- 一份证据包 JSON 样例：展示 `evidence_id`、source type、time window、local/global view、confidence、route status、arbitration status。
- 一个冲突仲裁例：ASR 暗示“free”，OCR 显示“limited time 50% off”，系统如何避免回答“免费”。
- 一个生成约束例：答案中每个关键声明后附 evidence ID，无法支撑的营销解读被降级为“可能/倾向于”。
