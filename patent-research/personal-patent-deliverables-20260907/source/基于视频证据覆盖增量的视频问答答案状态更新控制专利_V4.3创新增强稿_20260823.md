# 基于视频证据覆盖增量的视频问答答案状态更新控制专利 V4.3 创新增强稿

> 状态：创新增强初稿，不替代 V4.2，不是可直接递交的正式申请文件  
> 更新时间：2026-08-23  
> 目的：在 V4.2 的“同证据复评—声明迁移—闭包提交”基础上，进一步形成更集中的单一发明构思。

## 一、建议名称

**一种基于视频证据覆盖增量的视频问答答案状态更新控制方法、装置、设备及存储介质**

“覆盖增量”不是泛指多看几帧，而是指：针对问题要求的某个事实槽，新增视频证据使该事实槽对应的时空—区域—模态覆盖状态发生了可计算变化。

## 二、一句话核心

系统先把问题所需事实表示成视频证据覆盖单元；补证后、候选答案生成前，以不使用新旧答案候选槽值的方式生成并冻结覆盖增量记录；候选答案中的每项实质变化只有同时绑定该预先冻结的覆盖增量记录及其新增视频证据、并通过同一扩展证据快照核验时，才可随其依赖闭包原子写入，否则不写入并输出当前证据下的安全状态。

## 三、相对 V4.2 的真正升级

V4.2 要求“变化有本轮 ΔE 见证”。V4.3 再增加一层必要条件：

> 不能因为 ΔE 中碰巧存在一段相关证据就允许答案变化；必须先证明该 ΔE 把与该变化对应的必要差异槽从未覆盖或低覆盖变成已覆盖，且答案变化绑定的见证正是造成该覆盖变化的证据单元。

因此，V4.3 控制的是以下连续因果链：

```text
问题所需槽
  → 初始覆盖状态
  → 覆盖缺口
  → 定向取得 ΔE
  → 在 A2 前冻结覆盖增量记录 δC
  → A0/A2 同 E+ 复评
  → 声明迁移绑定 δC
  → 闭包准备写入
  → 全部获授权才提交
```

新增证据只是“相关”不够；新增证据必须造成与待变更事实槽对应的覆盖增量。

## 四、核心数据结构

### 4.1 证据覆盖单元 `CoverageCell`

每个覆盖单元至少包括：

- `cell_id`：覆盖单元标识；
- `required_slot_id`：问题要求的事实槽，例如价格值、价格单位、说话人、动作对象、时间先后或因果结果；
- `allowed_modalities`：允许用于覆盖该槽的证据模态，例如完整帧、局部区域、OCR、ASR；
- `time_span`：视频时间区间或待检索时间范围；
- `region`：全帧或归一化图像区域；
- `quality_requirements`：分辨率、OCR/ASR 置信信息、可读性或持续时长条件；
- `coverage_score`：当前证据集合对该单元的覆盖程度；
- `coverage_state`：未覆盖、部分覆盖或已覆盖；
- `evidence_ids`：造成当前覆盖状态的证据单元标识。

覆盖状态描述“用于判定该槽的证据是否已经取得且质量可用”，不直接表示某个候选槽值为真，避免把取证完整性和声明真实性混为一谈。

### 4.2 覆盖增量记录 `CoverageDeltaRecord`

每轮补证后，对受影响的覆盖单元生成：

```text
delta_id
cell_id
required_slot_id
before_snapshot_id
after_snapshot_id
before_score / after_score
before_state / after_state
incremental_evidence_ids
time_span / region / modality
gain_reason_code
created_before_candidate
record_digest（可选）
```

当 `after_score - before_score` 达到增量条件，或者覆盖状态由未覆盖/部分覆盖跨越为已覆盖时，记为正覆盖增量。覆盖增量记录在生成 A2 前写入不可变记录区，并与补证前后快照及增量证据标识绑定；一种实现可进一步对上述字段生成 `record_digest`。未形成正覆盖增量的 ΔE 可以保留用于审计，但不能单独授予实质答案变化的写入资格。

覆盖单元和覆盖评分由问题、事实槽类型、允许模态、视频位置、区域及证据质量确定，不使用 A0 或 A2 给出的候选槽值作为覆盖匹配目标。候选槽值是否真实，由之后在 E+ 下执行的声明支持/冲突核验决定。这样可以避免系统先看到候选答案，再事后选择与候选值相似的证据并反向制造覆盖增量。

### 4.3 声明迁移记录 `MigrationRecord`

在 V4.2 字段上增加：

- `necessary_difference_slot_id`；
- `required_delta_id`；
- `delta_witness_ids`；
- `verified_snapshot_id`；
- `authorization_state`；
- `authorization_failure_code`。

`required_delta_id` 将取证阶段的覆盖变化与写入阶段的答案变化直接连接。

## 五、机器可执行的覆盖计算示例

对问题所需槽 `k`，可采用如下可实施但非唯一的覆盖评分：

```text
C_k(E) = max_e [ align(e,k) × quality(e,k) × location_match(e,k) ]
```

其中：

- `align(e,k)` 表示证据与槽的语义匹配程度；
- `quality(e,k)` 表示该模态证据是否达到可读、可听或可辨识条件；
- `location_match(e,k)` 表示证据时间段和图像区域是否落入待覆盖范围；
- `e` 限定为证据集合 `E` 中模态属于该槽允许模态的证据单元。

本轮覆盖增量为：

```text
ΔC_k = C_k(E0 ∪ ΔE) - C_k(E0)
```

可以将以下任一规则作为正覆盖增量条件：

```text
ΔC_k ≥ γ_k
```

或：

```text
C_k(E0) < τ_k 且 C_k(E0 ∪ ΔE) ≥ τ_k
```

对于需要多个证据要素共同判定的槽，可以把一个槽拆成多个子单元，并要求预定义的必要子单元全部覆盖。例如“优惠价格”可拆为数值、货币/单位和优惠语境三个子单元。

## 六、实质变化的授权谓词

对实质迁移 `m`，定义：

```text
Authorize(m) =
    PositiveDelta(delta(m))
    ∧ Precommitted(delta(m), before_generation(A2))
    ∧ SlotMatch(necessary_slot(m), cell(delta(m)))
    ∧ WitnessSubset(witness(m), incremental_evidence(delta(m)))
    ∧ SameSnapshot(A0, A2, m)
    ∧ StateCondition(m)
```

其中：

- `PositiveDelta`：绑定的覆盖增量记录为正覆盖增量；
- `Precommitted`：覆盖增量记录在 A2 生成前已冻结并与对应证据快照保持身份一致，且其形成过程未使用 A0/A2 的候选槽值；
- `SlotMatch`：迁移的必要差异槽与覆盖增量对应的问题所需槽一致或满足预定义的子槽映射；
- `WitnessSubset`：见证证据属于该覆盖增量记录列明的本轮 ΔE；
- `SameSnapshot`：A0、A2 和该迁移都在相同 E+ 及相同核验配置下处理；
- `StateCondition`：新增、替换或撤回分别满足支持/冲突条件。

闭包 `K` 的提交条件为：

```text
Commit(K) = SnapshotValid(K) ∧ ∀m∈MaterialMigrations(K), Authorize(m)
```

只要一个实质迁移没有取得覆盖增量授权，闭包中的候选写入集合就不提交。

## 七、建议的独立权利要求骨架

### 权利要求 1（方法独权候选）

一种视频问答答案状态更新控制方法，包括：

1. 获取视频、问题、初始视频证据集合 E0 和基于 E0 生成的初始答案 A0；
2. 从问题确定一个或多个问题所需事实槽，并针对各问题所需事实槽建立证据覆盖单元，证据覆盖单元至少关联事实槽标识、允许证据模态、视频时间范围、图像区域条件和覆盖状态；
3. 根据 E0 中证据单元的证据模态、视频时间位置、图像区域和证据质量确定初始覆盖状态，并将未达到覆盖条件的证据覆盖单元确定为覆盖缺口；
4. 根据覆盖缺口从同一视频取得增量视频证据 ΔE，基于 ΔE 对对应证据覆盖单元重新计算覆盖状态，并生成覆盖增量记录；所述覆盖增量记录至少关联覆盖单元标识、补证前后覆盖状态、本轮增量视频证据标识以及扩展证据快照标识；
5. 在候选答案 A2 生成前冻结所述覆盖增量记录，其中覆盖单元定义和覆盖状态计算不以 A0 或 A2 的候选槽值作为匹配目标；将 E0 与 ΔE 固定为扩展证据快照 E+，以问题和 E+ 生成不接收 A0 语义内容作为改写输入的候选答案 A2，并在相同 E+ 和相同核验配置下分别核验 A0 与 A2；
6. 将 A0 与 A2 拆分并映射为原子声明，对实质变化建立声明迁移记录，声明迁移记录至少包括必要差异槽、拟写入状态和所需覆盖增量记录标识；
7. 仅在所需覆盖增量记录已在 A2 生成前冻结且与所述 E+ 保持身份一致、所述记录表示与必要差异槽对应的证据覆盖单元因本轮 ΔE 形成正覆盖增量、迁移见证证据属于该覆盖增量记录中的本轮增量视频证据、且新旧声明在 E+ 下满足对应迁移状态条件时，将该声明迁移确定为获授权迁移；
8. 根据原子声明之间的预定义依赖关系确定包含实质变化声明的受影响声明闭包，将闭包候选状态写入暂存集合；仅在闭包内全部实质变化均为获授权迁移且扩展证据快照仍有效时，原子提交所述暂存集合；否则丢弃所述暂存集合，并根据 E+ 下的声明支持状态输出保留、证据不足、撤回或拒答状态；
9. 仅根据已提交状态及 E+ 下仍受支持的保留状态生成最终答案。

### 为什么该独权仍是一项发明构思

独权中的各步骤不是独立叠加：

- 覆盖单元产生取证目标；
- 取证结果产生覆盖增量记录；
- 同一覆盖增量记录成为声明迁移的必要授权输入；
- 获授权迁移组成闭包的提交谓词；
- 提交结果决定最终可输出状态。

如果删除覆盖增量记录，补证与迁移提交之间的数据因果链断裂；如果删除同 E+ 复评，覆盖增量与新旧状态不可在同一口径下判定；如果删除闭包提交，互相依赖的获授权迁移可能部分写入。因此这些步骤在功能上互相支持。

覆盖增量记录在 A2 之前冻结，使它不是候选答案生成后的解释性标签，而是候选状态写入前已经存在的机器许可条件。

## 七点一、参考伪代码

```text
slots = derive_required_slots(Q)                 # 仅由问题和任务规则生成
cells0 = build_coverage_cells(slots, E0)
deficits = {c for c in cells0 if not covered(c)}

delta_evidence = acquire_video_evidence(V, deficits, budget)
E_plus = freeze_snapshot(E0, delta_evidence)
cells1 = recompute_coverage(slots, E_plus)        # 不使用 A0/A2 候选值
delta_records = freeze_before_candidate(
    diff(cells0, cells1), E_plus, delta_evidence
)

A2 = generate(Q, E_plus)                         # 输入不含 A0 语义内容
old_states = verify(split(A0), E_plus, verifier_config)
new_states = verify(split(A2), E_plus, verifier_config)
migrations = map_and_diff(old_states, new_states)

for migration in migrations:
    migration.authorized = (
        precommitted(migration.delta_id, delta_records)
        and positive_delta(migration.delta_id)
        and slot_match(migration.necessary_slot, migration.delta_id)
        and witness_from_bound_delta_evidence(migration)
        and transition_state_condition(migration)
    )

for closure in dependency_closures(migrations):
    stage(closure)
    if snapshot_valid(E_plus) and all_authorized(closure):
        atomic_commit(closure)
    else:
        discard_stage(closure)
        apply_safe_state(E_plus, closure)

return constrained_render(committed_and_supported_states())
```

## 八、建议的从属保护层

### 8.1 覆盖评分和质量条件

保护 `C_k(E)` 的构造，以及 OCR 置信信息、ASR 时间段质量、局部图像分辨率、跨帧重复和视频时间覆盖等质量项。

### 8.2 预算约束的覆盖增益选取

在 Token、帧数或计算预算下，按单位预算的预计覆盖增益选取候选完整帧、OCR 区域、局部裁剪或 ASR 时间段；该特征作为效率从属，不作为主创新。

### 8.3 多要素槽

对数量、价格、时间和因果槽拆分必要子单元；只有必要子单元达到预定义覆盖组合才形成正覆盖增量。

### 8.4 不对称迁移条件

- 新增：新声明受支持，且必要差异槽取得正覆盖增量；
- 替换：新声明受支持，旧声明冲突；或旧声明证据不足、新旧值互斥且 ΔE 正向支持新值；
- 撤回：旧声明存在来自 ΔE 的冲突见证；
- 表达压缩：不得改变规范化事实槽和值，不消耗实质迁移授权。

### 8.5 双域闭包

下游状态写入集合与上游只读证明集合分离；当一个闭包写入的事实槽被另一个闭包用作证明上下文时，触发后者重核验或闭包合并。

### 8.6 派生声明的覆盖增量血缘

当一个必要差异槽不是由视频单元直接感知，而是由已覆盖槽通过预定义确定性运算得到时，生成 `DerivedDeltaRecord`，至少记录上游 `delta_id` 集合、输入事实槽、运算符标识、输入快照版本和输出事实槽。只有全部上游覆盖增量仍有效、输入声明处于支持状态且按所记录运算符可复算得到唯一输出时，派生迁移才取得写入资格。

例如“优惠 20 元”可以由受支持的原价 79 元、现价 59 元及减法运算得到；模型仅用自然语言声称“优惠 20 元”而没有上述血缘记录时，不得写入。

### 8.7 覆盖增量复用限制

同一 `delta_id` 可以被多个迁移引用，但每个迁移必须分别满足必要差异槽匹配和声明状态条件；不得因一个覆盖单元形成正增量而对同一答案中的其他事实统一授权。

### 8.8 匹配反事实必要性

以同模态、近似时间位置、分辨率和输入预算匹配且经核验为非见证的证据替换见证证据；替换后对目标声明的支持程度下降达到条件时，确认该见证的必要性。该项宜作为强从属，不塞入方法独权。

### 8.9 快照版本校验

暂存记录携带 `verified_snapshot_version` 和证明引用集合版本；提交前比较当前版本。版本不一致时禁止提交并重新核验，以避免核验完成后证据或上游状态变化造成陈旧写入。

### 8.10 失效标记与恢复证明

对在快照版本 `v` 下进入冲突状态的旧声明写入失效标记。后续回退或重组不得输出版本早于该失效标记的旧状态；只有后续证据快照形成新的正覆盖增量并生成恢复见证时，才允许恢复该声明。

### 8.11 无新增声明终检

最终文本仅接收已提交或保留的声明标识、声明文本和证据标识；重新拆分后出现无法映射的新声明时删除并重组，仍失败则输出结构化状态或拒答。

## 九、四个实施例

### 9.1 成功替换

问题询问商品价格。E0 未包含价格出现的时间段，A0 输出“99 元”。价格值、单位和优惠语境三个覆盖子单元中，价格值单元为未覆盖。

系统在 11.2 秒局部区域取得 OCR 证据“限时 79 元”，形成 `delta_07`：价格值单元由未覆盖变为已覆盖，增量证据为 `O7`，时间为 11.2 秒，区域为对应文字框。A2 不接收 A0 文本而独立输出“79 元”。在 E+ 下，A0 的“99 元”处于冲突状态，A2 的“79 元”处于支持状态。替换迁移的必要差异槽为价格值并绑定 `delta_07/O7`，取得授权后提交。

### 9.2 相关补证但不授权变化

问题仍询问价格，ΔE 只取得商品标识清晰帧。该帧与商品相关，但价格值覆盖单元仍未覆盖，没有正覆盖增量记录。即使 A2 随机输出“79 元”，该迁移也因缺少对应覆盖增量授权而不写入。

### 9.3 闭包部分满足但整体不提交

A2 同时把“79 元”改为“59 元”，并据此新增“优惠 20 元”。价格替换有 OCR 覆盖增量，但优惠差值声明所需的原价或计算前提没有取得覆盖或支持，也没有可复算的派生覆盖增量血缘。二者位于同一依赖闭包，后者未获授权，因此候选闭包不提交；系统可保留 E+ 下仍受支持的其他声明，并对价格相关必填槽输出证据不足或继续取证。

### 9.4 快照变更导致重核验

A0/A2 在 E+ 版本 3 下完成核验并写入暂存集合；提交前，新的 ASR 段加入并形成版本 4，且该 ASR 段属于闭包证明上下文。版本校验失败，系统丢弃版本 3 的暂存集合并在版本 4 下重新核验，避免写入陈旧状态。

## 十一、现有实现支撑与缺口

### 已有可复用基础

- `EvidencePackage` 已有 `evidence_id`、`frame_id`、`timestamp`、`time_window`、全局/局部视图、OCR、ASR 和评分字段；
- `ClaimCheckPlan` 已能拆分声明，并按 OCR、ASR、时间窗口、全局/局部视图等确定所需证据；
- 检索记录已能保存 `supporting_evidence_ids`；
- 实验脚本已保存 OCR 的帧号、时间戳、归一化区域和置信信息，以及 ASR 起止时间和质量信息。

### 尚未实现，不能写成“已验证”

- `CoverageCell` 与覆盖评分；
- `CoverageDeltaRecord`；
- 声明迁移对 `delta_id` 的授权校验；
- 闭包暂存、快照版本比较和失效标记；
- V4.3 对应实验。

旧 Full‑7844 结果只能作为旧基线，不能证明 V4.3 的覆盖增量授权或闭包提交效果。

## 十二、建议的最小验证

不要求先做大数据集实验，但递交前最好做 30—100 个冻结样例，至少记录四种分支：

1. 补证形成正确覆盖增量并成功替换；
2. 补到相关但不覆盖必要差异槽的证据，错误 A2 被拒绝；
3. 闭包中一项无授权导致整体不提交；
4. 快照版本变化触发重核验。

建议最小对照：

```text
A0 基线
强制采用 A2
V4.2：同 E+ + ΔE 见证门控
V4.3：同 E+ + 覆盖增量授权 + 闭包提交
```

评价不必只看总体准确率，至少记录：无对应覆盖增量的错误变化拦截率、正确变化保留率、陈旧旧声明复活次数、闭包部分写入次数和平均新增证据预算。

## 十三、当前判断

- V4.3 比 V4.2 更能解释“为什么这些步骤不是堆叠”：同一个 `delta_id` 从补证一直传到提交判定。
- 它不是靠“覆盖图”“原子声明”或“事务”任何单点取得创新，而是靠覆盖变化对答案状态变化的机器授权关系。
- 模态追加检索、证据链、版本证明树及派生事实血缘已有较强在先基础，只能作为从属细节，不能与主创新并列宣传。
- 代价是实施成熟度下降：新核心尚未编码和实验，说明书必须给足覆盖计算、字段、状态表和失败分支。
- 在当前定向检索范围内，未发现单篇文献公开完整链条；但 D1 + REVEAL + CN121901431A + 通用事务控制仍可构成组合攻击，因此不能宣称创新性已经确定。

**推荐决策：把 V4.3 作为新的主方案蓝本；保留 V4.2 作为较宽备选文本。正式递交前，以 V4.3 独权骨架再做一次代理人级全文检索和旧案官方档案核验。**
